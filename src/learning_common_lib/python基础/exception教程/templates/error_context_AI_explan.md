### 这一节在介绍什么

这段 `error_context.py` 主要在演示一种**“在一次请求/任务的生命周期内，跨多层调用栈传递统一错误上下文”**的方法：用 `ContextVar` 保存一个 `ErrorContext`（包含 `request_id / user_id / operation / timestamp / extra`），在“入口处”（例如 Web 中间件、任务入口）设置，在任何深层函数里随时读取，用于日志、异常处理与排障。

核心结构是三件套：

- **`ErrorContext` dataclass**：承载“这次请求是谁、在做什么、发生在什么时候、额外信息是什么”
- **`error_context: ContextVar[ErrorContext | None]`**：把上下文绑定到“当前执行上下文”（通常对应一次请求、一次协程/任务链）
- **`set_context(...) -> (ctx, token)` / `reset_context(token)`**：用 token 做**成对的设置与恢复**，避免污染后续请求/任务

---

### 为什么要这么做（意义）

- **让日志和异常变“可关联”**  
  生产环境排障最难的是“同一次请求的日志分散在很多地方”。有了 `request_id` 等字段，你可以把所有层（handler/service/repo/SDK）打印的日志串起来。

- **减少参数层层传递的样板代码**  
  不用在每个函数签名里都加 `request_id, user_id, operation...`，也不用到处手动拼装。

- **适配异步场景（协程）**  
  `ContextVar` 设计目标之一就是在异步任务切换时仍能保持“当前上下文”，比用全局变量安全得多（全局变量会串请求）。

- **降低“跨请求数据泄漏”的风险**  
  这段代码刻意让 `ContextVar` 的默认值是 `None`，并且 `get_context()` 在没设置时返回 `_new_context()` 的**新对象**，避免 `extra` 这种可变字段在多个请求间共享。

- **`_new_context()`**（L18-21）  
  明确强调：默认上下文必须每次都是新对象，避免共享可变默认值（尤其是 `extra`）。

  定义上下文内容，并提供 `to_dict()`，用于结构化日志/错误响应（只在字段存在时输出，减少噪音）。

  这里的设计点是：**不直接 default 一个 `ErrorContext()`**，而是用 `None` 表示“未显式设置”，由 `get_context()` 决定返回新对象。

- **`get_context()`**（L57-63）

- **`set_context(**kwargs)`**（L65-77）

---

### 适用与不适用（这段文件头部已经点明）

- **适用**：单进程内的一次请求/协程链路，把上下文带到任意深度，用于日志、异常处理、返回错误信息时附带 request_id。
- **不适用**：**跨进程/跨服务**传递（需要分布式追踪体系，比如 trace/span、header 传递、链路追踪系统等），`ContextVar` 只在当前进程内生效。

---

### 你能把它怎么用在真实项目里

- **在 Web 中间件/请求入口**：生成 `request_id`，调用 `set_context(...)`，请求结束 `finally: reset_context(token)`
- **在统一异常处理器**：`ctx = get_context()`，把 `ctx.request_id` 打进日志、错误响应或告警事件里
- **在任意深层库代码**：无需改函数签名，直接 `get_context()` 取到当前请求信息

### ContextVar 在 FastAPI 异步并发下怎么“保证上下文不串”

结论是：`ContextVar` 不是“全局只有一份值”，而是**每个异步任务（准确说：每个 asyncio Task / 当前执行上下文）各自有一份独立的值**。所以客户端同时打 100 个请求时，通常会对应服务器端 100 个并发处理任务，每个任务里 `error_context` 都是“自己的那份”，互不影响。

---

### 具体机制（你可以把它理解成“协程局部变量”）

- **请求 A** 进入（中间件）→ `tokenA = error_context.set(ctxA)`
- **请求 B** 同时进入 → `tokenB = error_context.set(ctxB)`

之后哪怕执行在事件循环里不断切换：

- 当事件循环切回 **任务 A** 继续跑，`error_context.get()` 读到的是 `ctxA`
- 切到 **任务 B**，读到的是 `ctxB`

这种隔离不是靠锁，而是靠 Python 在调度协程时，会把当前 Task 关联的 **context（上下文字典）** 一起带着走；`ContextVar` 的读写就是在操作“当前 context”里的那份值。

---

### 为什么不会像全局变量那样串请求

- **全局变量**：所有协程共享同一份内存，调度一切换就可能被别的请求改掉，必串。
- **ContextVar**：值存放在“当前执行上下文”，调度切换会切换上下文，因此不会串。

---

### `token` 的意义（保证“进入-退出”成对）

`set()` 返回的 `token` 代表“设置之前的旧值”。在 `finally` 里 `reset(token)`：

- 防止同一个任务里后续逻辑（或复用的调用链）读到旧请求的上下文
- 更关键：在一些边界场景（同一 Task 内嵌套设置）能恢复到正确的上一层上下文

---

### 需要注意的边界场景（现实里最容易踩坑的点）

- **你把工作丢到线程池/新线程**（`run_in_executor` / `ThreadPoolExecutor`）  
  线程有自己的执行上下文，**不会自动继承**当前协程的 `ContextVar`（是否传播取决于你怎么切换/封装）。这时深层线程里的 `get_context()` 可能拿到默认值。解决通常是：把上下文显式传过去，或用 `copy_context()` 包装线程入口。

- **你创建后台任务**（`asyncio.create_task(...)`）  
  新 task 一般会**复制创建瞬间**的上下文快照：  
  - 创建时已经 `set_context()` → 后台任务能看到当时的 ctx  
  - 创建之后你又修改/重置 → 后台任务不一定跟着变（因为它是快照语义）

---

### 用一句话类比

把 `ContextVar` 当成：**“每个并发请求各自带着一个隐形的字典，函数不传参也能从字典里取到 request_id 等信息；事件循环切换任务时，也会把这个字典一起切换。”**

### 请求结束后，`ContextVar` 会不会“自动释放资源”？

- **会自动结束绑定，但不是你想的那种“释放动作”**：`ContextVar` 的值是挂在“当前任务的上下文（context）”上的。请求处理结束后，这个 **Task 不再被引用** → 会被 GC 回收 → **连同它的 context 一起回收**，因此不会无限累积。
- **但这不等于你可以不清理**：如果你在同一个 Task 里做了嵌套调用、或框架/中间件链路复杂、或有后台任务/线程池介入，**不 reset 仍可能造成逻辑污染**（后续代码在同一执行上下文里读到旧值），以及让某些对象存活更久。

---

### 最推荐的做法：在请求生命周期边界显式 reset（用 token）

你现在的模板已经给了正确范式：

- **入口（中间件）**：`ctx, token = set_context(...)`
- **出口（finally）**：`reset_context(token)`

这样做的价值是：无论成功/异常/提前返回，都能保证上下文恢复到“进入前状态”，不依赖 GC 时机。

---

### 什么时候“只靠自动回收”也行，什么时候不行？

- **基本可行**（但仍建议 reset）：普通 FastAPI 请求，每个请求一个 Task，且你不把上下文传播到别的执行单元。
- **强烈不建议只靠自动回收**：
  - **`asyncio.create_task`** 创建后台任务：新任务会复制创建时的上下文快照，可能导致“请求结束了但后台任务仍持有上下文对象”，从而延长它的生命周期。
  - **线程池/子线程**：上下文可能不传播或传播不符合预期，你更需要在边界清晰地 set/reset 或显式传参。
  - **长连接/流式响应/WebSocket**：一个“请求”可能持续很久，context 也会跟着存活很久，更要谨慎管理 `extra` 里放的对象大小。

---

### 实操建议（怎么“设置”才稳）

- **中间件统一做 set/reset**（`try/finally`），这是最稳的“一刀切”方案。
- **`extra` 里避免放大对象/DB session/请求体大块数据**：即使会回收，也会在请求期间增加内存压力；后台任务场景还会被拖得更久。
- **后台任务需要上下文时**：倾向于把必要字段（如 `request_id`）作为参数传入，而不是依赖“隐式捕获整份上下文”。
