# 中型企业面试题专项：多租户、信息安全、PII 校验与高并发

本文用于系统性回答 Agentic RAG 在中型企业生产落地时最常被追问的四类问题：

1. 多租户如何做隔离，避免串租与越权。
2. 信息安全如何落地，避免数据泄露、Prompt 注入、对象存储暴露和日志泄密。
3. PII（Personally Identifiable Information，个人身份可识别信息）如何识别、过滤与脱敏。
4. 高并发场景下如何保证系统稳定、状态正确、成本可控。

本文目标不是“讲概念”，而是给出一套至少能通过中型企业技术面试的生产级答法。文中尽量使用正式术语；对于难懂术语，会补充通俗解释。

---

## 1. 为什么面试官一定会问这四个点

在企业环境中，Agentic RAG 不是一个“会回答问题的模型应用”这么简单，它本质上是一个：

1. 带有检索、编排、缓存、异步任务、状态机的分布式系统。
2. 处理企业内部知识、文档、会话上下文和用户请求的业务系统。
3. 可能接触敏感数据、客户数据、财务数据、人事数据的安全敏感系统。

因此，面试官问这四个点，实际是在验证候选人是否具备以下能力：

1. 是否理解企业系统的风险边界，而不只是模型调用。
2. 是否知道哪些组件负责“正确性”，哪些组件负责“性能”。
3. 是否理解共享基础设施条件下的租户隔离和权限边界。
4. 是否知道大模型应用上线后最容易出事故的位置是什么。

一句话概括：

> 面试官不是在考你会不会 Redis、Celery、Milvus，而是在考你有没有“生产系统思维”。

---

## 2. 先给出一版适合面试的总回答

如果面试官只给你 1 到 2 分钟，你可以先用下面这段标准化表达：

> 在中型企业场景下，我会把 Agentic RAG 的生产方案拆成四个方面。第一，多租户采用共享基础设施下的逻辑隔离，核心表、缓存 Key、异步任务上下文、向量检索元数据和对象存储路径全部带 `tenant_id`，并通过 Repository 层和 ACL 强制过滤，避免串租。第二，信息安全上要覆盖密钥管理、传输加密、对象存储私有化、输入校验、Prompt Injection 防护、日志脱敏和审计追踪。第三，PII 不能只在最终答案上做正则，而应该做“入库打标、检索过滤、输出脱敏”三道门，必要时按权限做字段遮罩或直接拒答。第四，高并发下不让 API 挂住等待长任务，而是异步提交、编排与执行解耦，MySQL 负责状态真理源，Redis 负责热缓存和协调，结合幂等键、乐观锁、预算切片、超时、熔断和降级，保证系统在高负载下仍然稳定可控。

这段话的价值在于：

1. 先给出框架，证明你不是碎片化作答。
2. 强调“共享基础设施 + 逻辑隔离”的中型企业现实取舍。
3. 明确区分安全、PII 和高并发，不把三个问题混成一个“加几条规则”。
4. 提前抛出术语，如 `tenant_id`、ACL、幂等、乐观锁、熔断、降级，便于后续展开。

## 3. 多租户设计

### 3.1 什么是多租户

多租户（Multi-Tenancy）是指一套系统服务多个企业客户或多个组织单元。

每个租户都有自己的数据、用户、知识库、任务和权限边界。系统必须保证：

1. A 租户的数据不会被 B 租户读取到。
2. A 租户的任务不会误用 B 租户的缓存或异步结果。
3. A 租户的对象存储、日志、索引、搜索结果、会话上下文不会被 B 租户污染。

通俗理解：

> 多租户不是“多人用同一个系统”这么简单，而是“同住一栋楼，但每家门锁、快递箱、电表、水表都不能串”。

### 3.2 中型企业首选方案：共享基础设施下的逻辑隔离

对于中型企业，不建议一开始就做“一租户一套 MySQL、一租户一套 Redis、一租户一套向量库”。

原因如下：

1. 成本太高，运维复杂度不成比例。
2. 大多数中型企业项目的并发和数据量还不足以支撑物理隔离的收益。
3. 项目早期更需要统一治理和快速迭代，而不是过早拆散基础设施。

因此，更合理的首版方案是：

1. MySQL 共库共表，但所有核心业务表带 `tenant_id`。
2. Redis 共实例，但所有 Key 必须带租户前缀。
3. Celery 共 Broker，但任务上下文必须显式带 `tenant_id`。
4. 向量库 / ES 共集群，但所有文档元数据带 `tenant_id`、`kb_id`、`active_version_id`。
5. OSS 共 bucket 或分 bucket，但对象路径按租户分层。

这种方案叫：

> Shared Infrastructure with Logical Isolation  
> 共享基础设施 + 逻辑隔离

它的核心目标不是“物理独占”，而是“逻辑上绝不串租”。

### 3.3 多租户必须落在哪些层

#### 3.3.1 接口层

接口层必须从认证结果中解析出：

1. `tenant_id`
2. `user_id`
3. `roles`
4. `scopes`

然后把这些信息注入到整个请求上下文中。

要求：

1. `tenant_id` 不能由前端自由传入后直接信任。
2. 必须以认证令牌、网关透传字段或服务端会话为准。
3. 所有后续 Repository 和 Service 默认从上下文拿 `tenant_id`，而不是业务代码手填。

#### 3.3.2 数据库层

所有核心业务表都应包含 `tenant_id`，至少包括：

1. `knowledge_bases`
2. `documents`
3. `document_versions`
4. `document_chunks`
5. `search_tasks`
6. `task_plans`
7. `subtasks`
8. `subtask_runs`
9. `evidence_cards`
10. `task_events`
11. `sessions`
12. `session_turns`

设计原则：

1. 所有查询默认加 `WHERE tenant_id = ?`
2. 所有唯一约束都要考虑租户边界，如 `unique(tenant_id, kb_code)`
3. 所有外键查询和关联查询，也必须保持租户条件闭环

通俗解释：

> 不是表里“有 tenant_id 就算多租户”，而是所有读写路径都必须被它约束住。

#### 3.3.3 Redis 层

所有业务 Key 必须统一前缀，例如：

```text
rag:search:{tenant_id}:task:{task_id}:state
rag:search:{tenant_id}:task:{task_id}:plan:{ver}:indegree
rag:search:{tenant_id}:subtask:{task_id}:{code}:memory
rag:search:{tenant_id}:task:{task_id}:evidence
rag:search:{tenant_id}:task:{task_id}:budget
```

要求：

1. 不允许使用不带租户维度的全局 Key 保存业务状态。
2. 不允许不同租户复用同一份“任务缓存”。
3. 不允许 resume、checkpoint、锁 Key 漏掉租户维度。

#### 3.3.4 异步任务层

Celery 任务上下文必须显式带：

1. `tenant_id`
2. `task_id`
3. `plan_version`
4. `subtask_code`
5. `execution_id`

Worker 回写结果时，必须同时校验：

1. 该结果是否属于当前租户。
2. 是否属于当前活动计划。
3. 是否属于当前执行实例。

如果校验不通过：

1. 只能落审计记录。
2. 不能推进状态机。

这类机制叫做：

> Fencing（围栏机制）  
> 作用是防止旧任务结果、错租户结果、重复投递结果污染当前状态。

#### 3.3.5 检索与索引层

向量库、ES、甚至未来图数据库中的记录都必须带租户维度元数据，例如：

1. `tenant_id`
2. `kb_id`
3. `document_id`
4. `version_id`
5. `active_version_id` 或等价过滤条件

查询时必须至少带：

1. `tenant_id`
2. 当前知识库范围
3. 当前活动版本范围

如果只按 `kb_id` 或 `document_id` 过滤，而不加 `tenant_id`，就存在串租风险。

#### 3.3.6 对象存储层

对象路径建议采用：

```text
tenant/{tenant_id}/kb/{kb_id}/doc/{document_id}/ver/{version_no}/source
```

好处：

1. 容易按租户审计。
2. 容易做生命周期管理。
3. 避免“同 hash 文件跨租户复用”带来的归属不清与误删。

### 3.4 ACL、RBAC、ABAC 应该怎么理解

这是面试中很容易被追问的点。

#### ACL

ACL（Access Control List，访问控制列表）是最直接的权限模型。

含义：

1. 某个用户是否能访问某个资源。
2. 某个用户是否能查看某类知识库。

适合首版：

1. 实现简单。
2. 能快速形成租户级和知识库级隔离。

#### RBAC

RBAC（Role-Based Access Control，基于角色的访问控制）是按角色授予权限。

例如：

1. `admin` 可以管理知识库和任务。
2. `auditor` 可以查看审计日志。
3. `analyst` 可以发起检索但不能下载原始文档。

适合中期演进：

1. 角色稳定，权限可管理。
2. 适合中型企业组织结构。

#### ABAC

ABAC（Attribute-Based Access Control，基于属性的访问控制）是根据属性动态判断权限。

例如：

1. 用户部门 = 财务部，且资源分类 = 财务文档，才允许查看。
2. 请求来源 IP、时间段、终端安全等级满足条件才允许下载。

适合后期精细治理：

1. 表达能力最强。
2. 复杂度也最高。

面试时建议这样回答：

> 首版我会先用 `tenant_id + ACL` 完成租户隔离闭环，再在中期演进到 `RBAC`，如果业务有字段级和场景级访问控制，再引入 `ABAC`。不建议在首版把所有权限模型一起做满，因为复杂度会过高。

### 3.5 多租户章节的面试答题重点

面试官最想听到这 5 个关键词：

1. `tenant_id` 全链路透传
2. Repository 强制租户过滤
3. Redis/Celery/Checkpoint/锁都带租户维度
4. 向量索引和对象存储也要租户隔离
5. 首版逻辑隔离，后续再做物理隔离

## 4. 信息安全设计

### 4.1 信息安全不等于“加个鉴权”

企业信息安全至少要覆盖四层：

1. 身份与权限安全
2. 数据存储与传输安全
3. 应用输入与模型调用安全
4. 审计与追踪安全

如果只回答“我会做鉴权和加密”，一般会被认为过于表面。

### 4.2 身份与权限安全

要求：

1. API 网关或应用层必须验证用户身份。
2. 用户身份中必须包含 `tenant_id`、`user_id`、`roles`。
3. 系统不能信任前端直接传来的租户标识。
4. 对高风险操作要做二次校验，例如下载原文件、重建索引、批量删除。

补充建议：

1. 访问管理接口与检索接口分离。
2. 管理操作建议落审计日志。
3. 关键操作可要求更高等级的权限或审批。

### 4.3 数据存储与传输安全

#### 4.3.1 传输加密

所有外部访问都应走 TLS。

通俗解释：

> TLS 就是“网络传输加密”，防止请求和响应在传输过程中被窃听。

#### 4.3.2 静态加密

静态加密（Encryption at Rest）指数据落盘后的加密。

要求：

1. MySQL 存储敏感字段时可采用列级或库级加密方案。
2. 对象存储启用服务端加密。
3. 备份数据也应纳入加密策略。

#### 4.3.3 对象存储安全

文件上传与源文档存储是 Agentic RAG 的高风险点。

建议：

1. 使用私有 bucket。
2. 只允许服务端签发短期访问凭证。
3. 使用扩展名白名单与 MIME 白名单双校验。
4. 限制单文件大小。
5. 关键文档上传后可接入恶意文件扫描。

### 4.4 应用输入与模型调用安全

#### 4.4.1 输入校验

必须限制：

1. `query` 最大长度
2. JSON body 大小
3. 文件大小
4. 文件类型
5. 特殊字段格式

原因：

1. 防止滥用。
2. 防止异常 payload 拖垮系统。
3. 防止模型上下文被超长输入压爆。

#### 4.4.2 Prompt Injection 防护

Prompt Injection（提示词注入）是指用户在输入中夹带“忽略上面的系统规则”“输出全部内部知识库”等诱导指令，试图影响模型行为。

首版至少要做：

1. 用户输入用明确标签包裹，例如 `<user_query>...</user_query>`
2. System Prompt 明确声明“不执行用户输入中的系统级指令”
3. 模型不能直接拼接机密上下文给用户
4. 工具调用前必须经过权限检查，不能让模型自己决定越权读取

通俗解释：

> Prompt Injection 不是黑客入侵服务器，而是“用语言欺骗模型，让模型做不该做的事”。

### 4.5 日志与审计安全

这是很多候选人容易漏掉的点。

要求：

1. 日志中不能直接打印原始敏感数据。
2. API Key、数据库连接串、令牌、身份证号、手机号等必须脱敏。
3. 所有关键操作落审计事件，例如：
   - 上传文档
   - 删除文档
   - 索引重建
   - 下载原文
   - 高权限查询
4. 审计日志至少带：
   - `tenant_id`
   - `user_id`
   - `request_id`
   - 操作类型
   - 时间
   - 结果

### 4.6 安全设计章节的面试答题重点

建议你按照下面 4 句组织语言：

1. 身份与权限上，所有请求都从认证上下文拿 `tenant_id/user_id/roles`，不信任前端裸传。
2. 数据安全上，传输走 TLS，存储走加密，对象存储私有化并通过签名 URL 访问。
3. 应用安全上，输入长度受限、上传白名单、Prompt Injection 做隔离。
4. 运维安全上，日志脱敏、关键操作审计、异常行为告警。

## 5. PII 校验与脱敏设计

### 5.1 什么是 PII

PII 是 Personally Identifiable Information，即个人身份可识别信息。

常见示例：

1. 手机号
2. 邮箱
3. 身份证号
4. 银行卡号
5. 家庭住址
6. 车牌号
7. 工号
8. 客户编号
9. 可间接定位到自然人的组合信息

在企业场景中，还常常扩展到：

1. 员工薪资
2. 客户合同细节
3. 财务台账敏感字段
4. 医疗、法务、HR 信息

### 5.2 为什么不能只做“正则替换”

只用正则的方案存在三个问题：

1. 召回率不够，很多敏感信息不是固定格式。
2. 语义信息识别不到，例如“张三的家庭住址”这种组合型敏感信息。
3. 没有权限语义，系统不知道“命中了敏感数据但当前用户是否有权查看”。

因此，生产级 PII 治理通常采用三层机制：

1. 规则引擎
2. 语义识别
3. 权限决策

### 5.3 推荐的三道门设计

#### 第一门：入库前打标

文档上传或外部数据进入系统时，先进行敏感信息扫描。

为每个文档、chunk、证据卡增加元数据，例如：

1. `sensitivity_level`
2. `pii_categories`
3. `contains_pii`
4. `allowed_roles`

好处：

1. 后续检索阶段可以直接利用这些标签。
2. 不需要每次回答前都重新全量扫描原始文档。

#### 第二门：检索时过滤

当系统召回 chunk 或证据卡时，不能直接交给模型。

必须先判断：

1. 当前用户是否有权限查看该敏感等级内容。
2. 当前租户是否允许该数据在此任务中被使用。
3. 当前任务是否属于允许访问该数据的业务场景。

处理方式可以有三种：

1. 直接过滤掉该证据
2. 只保留脱敏摘要
3. 用更低粒度的信息替代

#### 第三门：输出前脱敏

最终答案生成后，必须经过输出治理。

推荐做“三重校验”：

1. 事实一致性校验
2. PII / 敏感信息校验
3. 引用对齐校验

其中 PII 校验可采用：

1. 正则规则
2. 关键词黑名单
3. ACL / 角色权限回查
4. LLM 辅助识别

命中后的处理策略：

1. 自动遮罩，例如手机号只展示后四位。
2. 自动摘要，例如“某员工”替代真实姓名。
3. 降级输出，只给趋势不给明细。
4. 直接拒答，如果属于高敏感或越权请求。

### 5.4 常用正式术语解释

#### DLP

DLP（Data Loss Prevention，数据泄露防护）是防止敏感数据被非授权传播的一整套策略。

PII 校验和脱敏，本质上属于 DLP 的子能力。

#### Masking

Masking（遮罩）是指保留部分内容、隐藏部分内容。

例如：

1. 手机号 `138****5678`
2. 邮箱 `li***@company.com`

#### Redaction

Redaction（编辑性删除）是直接将敏感信息删除或用统一占位符替换。

例如：

1. `[REDACTED]`
2. `[敏感信息已隐藏]`

#### Field-Level Access Control

字段级访问控制，是指即使一条记录可访问，也不代表其中每个字段都可见。

例如：

1. 可以看订单总额
2. 但不能看客户手机号和银行卡号

这类控制常用于 HR、财务、法务场景。

### 5.5 PII 章节的面试答题重点

你可以直接用下面这套表达：

> PII 治理我不会只做最终答案上的正则替换，而是做三道门。第一，文档入库时对 chunk 打敏感标签；第二，检索召回时结合用户角色和 ACL 做过滤，避免模型看到不该看的内容；第三，输出前再做正则、关键词、权限回查和 LLM 兜底识别，命中后按策略遮罩、摘要、降级或拒答。这样能把风险前置，而不是等答案都生成了才临时补救。

## 6. 高并发设计

### 6.1 高并发问题的本质

面试官问高并发，不是要你证明系统能承受互联网级千万流量。

在中型企业里，高并发通常意味着：

1. 同时有多用户提交长任务。
2. LLM 调用和检索调用耗时较长。
3. 子任务并行执行带来状态竞争。
4. Redis、MySQL、Celery、SSE 会形成资源争抢。
5. 高峰期成本和队列积压可能失控。

通俗解释：

> 企业里的“高并发”更多是“长任务很多且都不短”，而不是单纯 HTTP QPS 很高。

### 6.2 正确的系统拆分方式

不建议让 FastAPI 请求线程一直挂着等待 Deep Search 结束。

正确做法是：

1. API 层快速接受请求并返回 `request_id`
2. `GlobalGraph` 负责控制流
3. `Celery` Worker 负责执行子任务闭环
4. `resume_orchestrator` 负责恢复编排
5. SSE 负责实时进度

这背后的核心思想是：

> Control Plane / Data Plane Separation  
> 控制面和数据面分离

其中：

1. 控制面负责状态机、DAG、任务推进、审计、预算、等待原因。
2. 数据面负责证据卡、输出、Redis staging、索引写入、对象内容。

### 6.3 高并发下最重要的五个技术点

#### 6.3.1 API 异步提交，避免长连接阻塞

接口层不能同步等待整个搜索任务完成。

推荐：

1. `POST /search` 返回 `202 Accepted`
2. 返回 `request_id`
3. 前端通过 SSE 或轮询获取进度

这样可以避免：

1. API Worker 被长任务占满
2. 反向代理超时
3. 请求级上下文过长导致资源浪费

#### 6.3.2 编排与执行解耦

LangGraph 负责：

1. DAG 规划
2. READY 计算
3. Replan
4. Finalize

Celery 负责：

1. 子任务执行
2. 检索与评估
3. 重试与超时
4. 后台刷库和维护任务

这样做的好处：

1. 编排逻辑清晰
2. 执行可以横向扩展
3. 单个子任务失败不会拖垮整个编排

#### 6.3.3 MySQL 保证正确性，Redis 负责性能

这是面试里非常关键的一句话。

必须明确：

1. MySQL 是真理源，保证状态正确。
2. Redis 是热缓存和协调层，负责性能，不负责最终真相。

应用到具体设计上：

1. 子任务状态流转依赖 MySQL 条件更新和 `row_version`
2. READY 计算可借助 Redis `HINCRBY + Lua`
3. 预算热计数放 Redis
4. Checkpoint 放 Redis
5. Redis 故障时可回退 MySQL 重建

通俗解释：

> MySQL 像账本，Redis 像便签纸。便签纸丢了可以重写，但账本不能错。

#### 6.3.4 幂等与防重

高并发和异步重试场景下，重复执行是常态，不是异常。

所以必须做：

1. 幂等键
2. 条件更新
3. 执行实例 fencing

关键设计：

1. 每次执行生成唯一 `execution_id`
2. `READY -> RUNNING` 必须带期望旧状态条件
3. Worker 回写结果时同时校验 `tenant_id + task_id + plan_version + subtask_code + execution_id`
4. 如果校验失败，则结果视为 stale，只落审计，不推进状态

#### 6.3.5 限流、预算、超时、熔断、降级

这是高并发治理的五件套。

##### 限流

Rate Limiting（限流）用于保护系统不被单租户打爆。

推荐：

1. 普通接口：每租户 100 req/min
2. 搜索接口：每租户 20 req/min

##### 预算

Budget（预算）是指每个任务可用的资源上限，例如：

1. LLM token
2. 检索次数
3. 最大耗时

作用：

1. 防止某个任务无限重试
2. 控制成本
3. 提升系统可预测性

##### 超时

多层超时建议：

1. 单次 LLM 调用：5-15 秒
2. 单路检索：3-10 秒
3. 子任务总超时：30-60 秒
4. 全局任务超时：120-300 秒

##### 熔断

Circuit Breaker（熔断器）是指某个依赖连续失败后，暂时不再继续调用它，避免把故障扩大。

通俗解释：

> 熔断器像家里的空气开关，线路短路时先跳闸，避免整个系统烧掉。

##### 降级

Degradation（降级）是指系统在资源不足或依赖异常时，不追求完整结果，而返回“部分可用结果 + 不确定性说明”。

这比直接报错更符合企业业务需求。

### 6.4 推荐的 Worker Lane 设计

在中型企业首版里，建议拆成 4 条主队列：

1. `subtask_jobs`
2. `orchestrate_jobs`
3. `persist_jobs`
4. `maintenance_jobs`

各自职责：

1. `subtask_jobs` 跑子任务检索、评估、校验闭环
2. `orchestrate_jobs` 跑编排恢复、Replan、Finalize
3. `persist_jobs` 异步刷数据面到 MySQL
4. `maintenance_jobs` 跑 reaper、对账、修复、清理

这种拆分的好处：

1. 避免重任务和轻任务抢同一批 Worker
2. 避免编排恢复被检索任务堵住
3. 容易按队列扩容
4. 容易做故障隔离

### 6.5 高并发章节的面试答题重点

建议按下面顺序回答：

1. API 异步提交，不阻塞等待长任务
2. 编排和执行解耦，LangGraph 管控制流，Celery 管执行
3. MySQL 保证状态正确，Redis 提供热缓存和协调
4. 通过 `row_version + execution_id + plan_version` 做幂等和防重
5. 用限流、预算、超时、熔断、降级保护系统

## 7. 四个主题之间的关系

这四个问题不是独立的，它们之间是联动关系：

### 7.1 多租户和安全

如果没有租户隔离，信息安全就是空谈。

因为最大的安全事故之一，就是“串租”，即把 A 租户数据返回给 B 租户。

### 7.2 安全和 PII

PII 是信息安全中的高敏感子集。

如果系统有鉴权，但没有 PII 治理，就会出现：

1. 模型看到了不该看的敏感字段
2. 最终答案把个人信息原样吐给用户

### 7.3 高并发和安全

高并发下更容易暴露安全问题，例如：

1. 任务回写错乱导致越权结果串入
2. 缓存 key 漏租户维度导致串租
3. 限流缺失导致某个租户恶意占满资源

### 7.4 高并发和 PII

高并发下如果只在最后一层做 PII 检查，会带来：

1. 模型上下文中已经看到了敏感信息
2. 异步日志、缓存、staging 中也可能保留了敏感内容

因此更稳妥的方案是：

> 敏感信息治理要前置，不要全部压到最终回答阶段。

## 8. 中型企业推荐落地方案

下面给出一版适合面试作答的中型企业推荐方案。

### 8.1 总体原则

1. 首版采用共享基础设施 + 逻辑隔离
2. MySQL 作为唯一真理源
3. Redis 作为热缓存、checkpoint 和短 TTL 协调层
4. Celery 承担异步执行
5. 所有控制面数据必须可审计
6. 所有敏感数据必须可识别、可过滤、可脱敏
7. 所有高风险依赖必须有超时、重试、熔断和降级

### 8.2 多租户推荐方案

1. 所有核心表增加 `tenant_id`
2. 所有 Repository 查询强制注入 `tenant_id`
3. Redis Key 统一前缀 `rag:{tenant_id}:...`
4. 向量库 / ES 元数据带 `tenant_id`
5. 对象存储路径带 `tenant_id`
6. 所有异步任务上下文都带 `tenant_id`
7. 日志、审计、指标都带 `tenant_id`

### 8.3 信息安全推荐方案

1. 认证结果中统一透传 `tenant_id/user_id/roles`
2. 密钥与连接串通过环境变量注入
3. TLS + 静态加密 + 私有 bucket + 签名 URL
4. 输入长度限制、文件类型白名单、Prompt Injection 隔离
5. 日志脱敏、关键操作审计、异常告警

### 8.4 PII 推荐方案

1. 文档入库扫描并打敏感标签
2. 检索前按 ACL/角色过滤敏感 chunk
3. 输出前做正则 + 关键词 + ACL 回查 + LLM 兜底
4. 命中后按策略遮罩、摘要、降级或拒答
5. 高敏感业务逐步演进到字段级访问控制

### 8.5 高并发推荐方案

1. API 异步提交 + SSE 进度
2. LangGraph 控制流，Celery 执行流
3. Worker lane 拆分
4. MySQL 真理源 + Redis 热数据
5. 幂等键、乐观锁、fencing、防重
6. 限流、预算、超时、熔断、降级
7. 用监控和审计形成闭环

## 9. 面试时最容易踩的坑

### 9.1 只说“我会加 tenant_id”

问题：

1. 没说 Redis、Celery、向量库、OSS 怎么隔离
2. 没说权限闭环

更好的说法：

> `tenant_id` 只是数据模型入口，真正关键的是全链路透传和全路径强制过滤。

### 9.2 只说“我会做加密和鉴权”

问题：

1. 太泛
2. 缺乏工程落点

更好的说法：

> 我会分成身份权限、传输与静态加密、应用输入安全、日志审计四层治理。

### 9.3 只说“PII 用正则脱敏”

问题：

1. 过于初级
2. 没有权限语义
3. 没有生命周期治理

更好的说法：

> PII 要做入库打标、检索过滤、输出脱敏三道门。

### 9.4 只说“高并发用 Redis 和 Celery”

问题：

1. 没说状态正确性
2. 没说防重和资源保护
3. 没说降级策略

更好的说法：

> Celery 只是执行引擎，真正的关键是异步提交、控制执行解耦、MySQL 真理源、幂等 fencing、限流预算超时熔断降级。

## 10. 一版完整的面试标准回答

下面是一段适合中型企业技术面试的完整回答，你可以直接背诵并按场景裁剪。

> 如果从中型企业生产落地角度设计 Agentic RAG，我会重点处理四件事。  
> 第一是多租户隔离。首版我不会上来就做一租户一套基础设施，而是采用共享 MySQL、Redis、对象存储和检索集群，但所有核心表、缓存 Key、异步任务上下文、向量索引元数据和对象路径都带 `tenant_id`，并通过 Repository 层和 ACL 强制过滤，防止串租。  
> 第二是信息安全。我会从四层治理：身份权限、传输与存储加密、应用输入安全和审计追踪。具体包括 TLS、私有 bucket、签名 URL、密钥环境变量管理、输入长度限制、上传白名单、Prompt Injection 隔离、日志脱敏和关键操作审计。  
> 第三是 PII 治理。不能只在最终答案上做正则替换，而要做三道门：入库时对文档和 chunk 打敏感标签，检索时按角色和 ACL 过滤敏感证据，输出前再做正则、关键词、权限回查和 LLM 兜底识别，命中后按策略遮罩、摘要、降级或拒答。  
> 第四是高并发治理。我不会让 API 挂着等 Deep Search 完成，而是采用异步提交、SSE 反馈、LangGraph 控制流和 Celery 执行流解耦。MySQL 负责状态真理源，Redis 负责热缓存和协调；通过乐观锁、幂等键、execution fencing 保证状态正确；通过 per-tenant 限流、预算切片、超时、熔断和降级来保护系统。这样即使在中型企业高峰流量下，也能保证系统稳定、结果可追溯、故障可恢复。

## 11. 最后总结

真正能打动中型企业面试官的，不是你会背多少组件名字，而是你能否说清楚下面这组关系：

1. 多租户解决“谁的数据属于谁”
2. 信息安全解决“谁能看到什么”
3. PII 治理解决“即使能查，也不能无边界暴露什么”
4. 高并发治理解决“在很多人同时使用时，系统如何不乱、不慢、不炸”

如果你能把这四句话讲顺，再加上前文的术语和落地方案，基本就已经具备生产级回答的框架了。

## 12. 建议你背熟的关键词

建议至少熟悉下面这些术语：

1. Multi-Tenancy：多租户
2. Logical Isolation：逻辑隔离
3. ACL / RBAC / ABAC：三类权限模型
4. Encryption in Transit / at Rest：传输加密 / 静态加密
5. Prompt Injection：提示词注入
6. PII：个人身份可识别信息
7. DLP：数据泄露防护
8. Masking / Redaction：遮罩 / 编辑性删除
9. Control Plane / Data Plane：控制面 / 数据面
10. Idempotency：幂等
11. Optimistic Lock：乐观锁
12. Fencing：围栏机制，防旧结果污染
13. Rate Limiting：限流
14. Budgeting：预算控制
15. Timeout / Retry / Circuit Breaker / Degradation：超时 / 重试 / 熔断 / 降级

如果这些词你能用自己的话解释清楚，面试就不会显得“只会背概念”。
