RAG 知识库管理与数据更新
•	RAG 知识库 CURD 常见问题：
￮	RAG 知识库搭建需要对这个知识库的文件文档进行动态更新了，那么你是用的全量嵌入还是增量处理？如果是增量的话，那么怎么来避免新旧文档导致的检索偏差问题？
￮	RAG 如何保证 mysql、milvus、es 数据的一致性？

•	在构建企业级RAG系统时，针对知识库的创建与动态更新，通常遵循以下原则和最佳实践：
￮	更新时，选择全量嵌入或增量嵌入？
除非数据量极小（例如几百个文档）或者处于开发测试初期，否则必须使用增量处理。
▪	全量嵌入：每次更新都清空向量数据库，重新读取所有文件，重新切片、Embedding 并入库。
▪	增量嵌入：仅对新增、修改或删除的文档进行处理。
￮	所谓的“检索偏差”或“新旧文档冲突”，通常指以下几种情况：
▪	幽灵数据：文档应已经删除，但其切片的向量依然存在于向量库或全文检索库
▪	版本冲突：文档更新了，但其旧文档的切片没有删除干净，用户检索时同时搜索到旧版与新版切片（甚至旧版的切片评分更高）
▪	碎片化：频繁增删导致向量索引结构（如 HNSW）索引性能下降
￮	要解决以上问题通常需要建立严谨的数据管道（Data Pipeline），以下是一些方案
▪	基于唯一标识符 (DocID) 的“先删后插”机制
•	原理： 每一个源文件（File）在进入系统时，必须分配一个全局唯一的 DocID。所有的切片（Chunks）在存入向量库时，必须在 Metadata 中携带这个 DocID。
•	更新流程：
￮	监测到文件 A 发生变更。
￮	Delete： 在向量库中，根据 Metadata.DocID = 'A' 删除所有旧的向量切片（工程上一般在Mysql 侧仅仅进行软删除）。
￮	Insert： 对文件 A 的新内容进行切片、Embedding，写入向量库。
•	作用： 确保向量库中永远只有该文档的“最新状态”，物理上杜绝了新旧版本共存的可能性。
▪	文件指纹 (File Hash) 检测
•	原理： 在处理文档前，计算文件的哈希值（如 MD5 或 SHA-256）。
•	数据库设计： 维护一张关系型数据库表（如 MySQL/PostgreSQL），记录：[文件名, DocID, File_Hash, Last_Updated_Time]。
•	判断逻辑：
￮	扫描文件时，计算当前 Hash。
￮	对比数据库中的 Hash。
￮	如果 Hash 没变 -->  跳过（节省计算资源）
￮	如果 Hash 变了  -->  触发“先删后插”流程，并更新数据库中的 Hash。
▪	元数据过滤与时间加权 (Metadata Filtering & Recency)
如果你需要保留历史版本（即不删除旧文档，而是归档），或者担心旧知识干扰，可以利用元数据。
•	版本控制： 在向量元数据中加入 version 或 publish_date。
•	检索过滤 (Pre-filtering)： 在查询向量库时，增加过滤条件，例如 filter: { version: "v2.0" } 或 timestamp > 2023-01-01。
•	重排序 (Rerank)： 在检索召回后，利用 Rerank 模型或手动逻辑，对结果进行加权。如果两个切片相似度相近，优先展示 timestamp 更近的切片。
▪	定期索引优化 (Index Optimization)
向量数据库（尤其是基于 HNSW 算法的）在频繁增删（尤其是删除）后，图结构会变得碎片化，导致检索精度（Recall）下降或延迟增加。
•	操作： 就像电脑磁盘整理一样，需要定期（如每周或每天低峰期）触发向量数据库的 Compact、Optimize 或 Rebuild Index 操作，清除已标记为删除的节点，重建图连接。

数据库的组成
￮	OSS 对象存储：物理源数据（Raw data）
￮	Mysql：源数据解析后的知识文档、Chunks、业务元数据等（Source of Truth，唯一真理源基准）
￮	Redis：缓存，这里用于轻量级消息队列MQ（redis stream）
￮	Milvus：文档 Chunks 向量库
￮	ElasticSearch：文档 Chunks 全文检索库

具体方案思路如下
核心原则是：以 MySQL 为状态机（State Machine）核心，Milvus 和 ES 视为 MySQL 的“投影”，允许短暂延迟，但必须最终一致。
•	唯一真理源 (Single Source of Truth): MySQL 记录一切状态。如果 Milvus/ES 挂了，可以从 MySQL 重建索引；如果 MySQL 挂了，业务就停了
•	软删除: 生产环境尽量不立即物理删除。删除只是修改MySQL状态，然后MQ异步清理 OSS/Milvus/ES
•	幂等性 (Idempotency): 所有的解析和索引操作必须支持重复执行而不产生副作用（例如：重复索引不会导致向量库里出现两条一样的数据，需要 Hash 文件指纹）
•	最终一致性: 上传后允许有秒级的搜索延迟，但不能有数据错误

1. 文件上传/更新 (避免重复与版本冲突)
在 User --> API 阶段：
￮	计算 Hash： 接收文件流时即计算 Hash
￮	查重：
▪	如果 file_hash 存在且状态为 COMPLETED：直接返回“秒传成功”（复用旧 ID），或者提示已存在
▪	如果 doc_id 存在但用户强制更新（覆盖）：
•	标记旧 doc_id 的状态为 DELETED_PENDING（待清理，此时用户API检索时将不会检索到这个文档，后续可以使用 MQ 异步清理）
•	创建新 doc_id 处理新文件。这是避免检索偏差最安全的做法：永远不修改向量，只增删

2. 解析与入库 (MySQL 作为真理源)
在 Parser --> MySQL 阶段：
￮	事务写入： Parser 解析完成后，在一个数据库事务中做两件事：
▪	写入 document_chunks 表（所有切片）
▪	更新 documents 表状态为 PARSED
￮	失败处理： 如果解析失败，更新 documents 状态为 FAILED 并记录错误信息

3. 索引双写一致性 (最关键的 Milvus + ES)
在 MQ_Index --> EmbedSvc/ESSvc 阶段，这是最容易出问题的地方，为了保证 Milvus 和 ES 都成功 的原子性，可以将两个过程同一线程异步双写，只有都成功时才算写入成功
￮	取数： Index Worker 从 MySQL 获取 doc_id 对应的所有 chunks
￮	执行向量化 & ES 写入：
▪	并发调用 Embedding API
▪	操作 A： 向 Milvus 插入向量（携带 doc_id 作为 Scalar 字段，chunk_id 为 PK）。
▪	操作 B： 向 ES 插入文档（同样携带 doc_id）。 
￮	原子性保障（同一线程异步双写）：
▪	只有当 Milvus 和 ES 都成功 时，才去更新 MySQL 状态为 COMPLETED
▪	如果任一失败：
•	捕获异常
•	执行回滚操作（Best Effort）：根据 doc_id 删除 Milvus 和 ES 中已写入的部分数据
•	MQ 消息不确认（NACK），利用 MQ 的重试机制稍后重试
•	达到最大重试次数后，标记 MySQL 状态为 INDEX_FAILED，需人工或定时任务介入

4. 如何处理删除
当用户更新文档（触发增量更新）时，实际上是“新文档入库 + 旧文档删除”。
￮	删除流程（异步清理）：
▪	用户发起删除请求。
▪	第一步（快速）： 仅在 MySQL 中将 documents 表状态置为 DELETED。此时业务层查询 API 会过滤掉该状态，用户立刻看不到该文件（逻辑删除）。
▪	第二步（异步）： 发送消息到 MQ_Cleaner。
清理 Worker：
￮	根据 doc_id 从 Milvus 删除：expr = "doc_id in [123]"。
￮	根据 doc_id 从 ES 删除。
￮	从 OSS 删除源文件。
￮	（可选）物理删除 MySQL 记录或归档。

5. 兜底方案：定期对账
即使有上述机制，消息队列可能会丢，网络可能会断，导致 MySQL 是 COMPLETED，但 Milvus 里缺数据。需要一个“清洁工（Janitor）”子进程定期巡查，删除幽灵数据与扩增缺失数据
￮	每日/每周定时任务：
▪	遍历检查： 随机抽取（或全量扫描）MySQL 中状态为 COMPLETED 的 doc_id
▪	Count Check：
•	MySQL 中该 doc 有 50 个 chunks
•	去 Milvus 查询 count(*) where doc_id=xxx
•	去 ES 查询 count
▪	自动修复：
•	如果数量不一致，触发“重建索引”事件（发送消息给 MQ_Index），利用幂等性覆盖写入
